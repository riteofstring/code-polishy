# Repository Output Cleanup

Repository outputs need explicit cleanup because accumulated reports and test
output can consume substantial local storage. Installed-release cleanup remains
the default; `--reports` and `--artifacts` select repository outputs instead.
The CLI parses scopes and renders one plan. The engine selects and removes
repository output, while the test artifact boundary retains ownership of its
completion and lease rules.

A canonical report is recognized by its command, digest-shaped directory,
protocol, and matching recorded report path. A gate candidate is removable only
when every execution has a completed report with matching gate, candidate, and
execution identities. The whole candidate is removed together, including its
latest pointer and logs, so the next gate observes absent evidence rather than
a stale pointer to a removed execution. Incomplete candidates remain intact.
Cleanup inspects existing identities; it does not calculate new hashes or
authenticate reusable evidence merely to delete regenerable output.

The `test-receipts`, `security-scans`, and `security-refresh` directories are
owned caches. Report cleanup removes them as whole trees, including cached
audits, individual uncached scan attempts, and security refresh records. These
records can all be regenerated; cleanup does not parse their contents or require
an installed release to reclaim them. The next verification scans again instead
of reusing removed evidence. Behavior-review,
architecture-review, and capability-upgrade directories are retained because
their evidence can encode decisions and input that cannot be regenerated by
rerunning checks. Other user files remain outside recognized generated trees.
Files added inside an owned report tree or cache share its lifetime.

Artifact cleanup reuses the automatic retention selector: the ownership manifest
must be valid and completed, the active lease must be absent, and the tree must
contain only regular files and directories. Explicit cleanup removes all such
executions instead of retaining the most recent three. It does not infer that an
active lease is abandoned or introduce process-liveness tracking. Reports and
receipts retain their recorded artifact metadata when artifact files are pruned,
just as they do after ordinary retention.

Planning precedes deletion and the dry run uses that same plan and byte counts.
Deletion uses a repository-root handle; linked output roots fail and trees with
linked or special entries are kept. Sizes describe logical bytes, not filesystem
allocation. Repository cleanup is run after other commands finish; it does not
coordinate concurrent report writers. Removal failures are operational errors
and only completed removals contribute to the result.
