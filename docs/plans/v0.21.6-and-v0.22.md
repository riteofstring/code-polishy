# v0.21.6 and v0.22 Roadmap

Status: proposed

## Outcome

v0.21.6 removes three immediate adoption failures without widening the release:

1. policy-owned Python analysis cannot mutate a sealed installation;
2. Vulture understands statically provable Pydantic reachability; and
3. `merge-gate` can govern the first commit that adopts Code Polishy.

v0.22 then adds portable release distribution, managed test artifacts, and a
separate test-ownership boundary. These are engine capabilities that future
official language packs can reuse, but v0.22 does not move built-in languages
into packs.

The existing
[language-pack discovery](universal-language-pack-capabilities.md) and
[first-party language-pack](installable-first-party-language-packs.md) plans
remain authoritative for pack protocol and migration decisions. This roadmap
does not duplicate or silently advance those cutovers.

## Shared constraints

- Keep one release manifest and content digest as the authority for installed
  bytes, regardless of whether a release arrives through an archive or OCI.
- Never execute target Python or import target Pydantic to discover framework
  behavior.
- Treat only an exactly absent base configuration as an unmanaged baseline.
  Unreadable, malformed, ambiguous, or removed policy remains an error.
- Keep command exit status authoritative. Test artifacts add evidence; they do
  not turn a failed command into a pass.
- Keep production module direction separate from test ownership.
- Use module size and dependency concentration as review information, not as
  arbitrary blocking thresholds.
- Add no new runtime dependency for v0.21.6. Use bundled Python's `ast`, the
  existing Vulture integration, the existing Git boundary, and the release
  manifest verifier.
- Run focused tests while implementing. Run supplemental suites once only after
  a stable release candidate exists, then rerun only invalidated suites.

## v0.21.6: adoption correctness

### 1. Prove sealed Python execution is immutable

The carried Python and Vulture command already uses isolated mode and disables
bytecode writes. Make that guarantee explicit and regression-proof.

Implementation:

1. Give every policy-owned Python invocation one command-construction boundary.
2. Require isolated execution and disabled bytecode generation at that boundary.
3. Put every writable home, cache, temporary file, and tool output outside the
   installed release.
4. Keep launcher manifest verification before every installed command.
5. Add an explicit final manifest verification after sequential Python quality,
   architecture, doctor, and gate commands.
6. Assert that the release gained no `__pycache__`, `.pyc`, missing, changed, or
   unrecorded file.

The test must exercise an installed, content-addressed release rather than a
source checkout. It must fail if any command mutates the release even when that
command is the last command in the sequence.

Filesystem permissions may add defense in depth where platforms support them,
but the portable contract is stronger: commands receive no writable path inside
the release, and complete manifest verification detects any changed byte or tree
entry.

### 2. Add exact Pydantic reachability

Extend the policy-owned Python AST analysis before generating Vulture
whitelists. Recognize a framework contract only when imports, aliases,
inheritance, and decorators prove that it is Pydantic.

Initial supported facts:

- direct and aliased `pydantic.BaseModel` subclasses;
- direct and aliased `pydantic_settings.BaseSettings` subclasses;
- local subclasses whose ancestry resolves to a proven model class;
- annotated model fields and supported field declarations;
- `model_config` inside a proven model class;
- `field_validator`, `model_validator`, `field_serializer`,
  `model_serializer`, and `computed_field` methods;
- Pydantic v1 `validator` and `root_validator` methods while those names remain
  part of the supported Pydantic contract; and
- qualified decorator calls and exact imported aliases of those decorators.

The resolver must not infer reachability from a bare method name, decorator
suffix, wildcard import, computed base class, or unresolved alias. Unsupported
reflection and plugin callbacks continue to use exact
`scope.pythonDynamicReferences`. Stale declarations, missing symbols, and
wildcards remain errors.

Generate the Vulture-specific whitelist internally from validated symbol facts.
Do not add target-controlled Vulture configuration or import Pydantic from the
target environment.

Conformance fixtures must prove that:

- model construction and serialization keep declared fields reachable;
- all supported validator, serializer, and computed-field forms stay live;
- aliases do not broaden matching to unrelated classes or decorators;
- ordinary unused fields, functions, and methods still fail at Vulture's 60%
  baseline;
- nested projects and custom source roots use their existing project inventory;
  and
- exact dynamic declarations remain necessary for genuinely reflective entry
  points.

### 3. Support first-time adoption in `merge-gate`

Define four base/candidate states explicitly:

| Base configuration | Candidate configuration | Result                            |
| ------------------ | ----------------------- | --------------------------------- |
| absent             | valid and newly added   | first-adoption full gate          |
| valid              | valid                   | ordinary governed merge gate      |
| valid              | absent                  | fail: governed policy was removed |
| absent             | absent                  | fail: candidate is not governed   |

An unreadable, malformed, non-regular, or ambiguous base configuration is not
“absent” and must fail. The same rule applies when `--config` selects a
non-default contained path.

For a first-adoption gate:

1. Resolve the exact merge base and prove the configured path is absent there.
2. Load and validate the candidate configuration and candidate lock normally.
3. Mark the configuration addition as policy-sensitive and select the full
   ordinary gate.
4. Use candidate ownership, scope, commands, suites, providers, and exceptions
   for candidate checks.
5. Do not require a base suite definition, base receipt, or base-policy replay
   from a repository that had no policy.
6. Never interpret the unmanaged base as passing evidence or use it to suppress
   a candidate failure.
7. Record `first-adoption` and the exact absent base path in the gate report.

Behavior-review policy must receive the same explicit first-adoption state. A
candidate may enforce evidence it can validly produce, but the engine must not
invent pre-adoption receipts or silently claim that an unmanaged base satisfied
incoming policy.

Fixtures must cover a passing candidate, every candidate check level failing,
custom configuration paths, a malformed base file, configuration removal, a
missing candidate lock, and a source-changing adoption commit. At least one
installed-release fixture must start from a commit containing no Code Polishy
files and run the candidate's `merge-gate` successfully.

### v0.21.6 documentation and release proof

Update the adoption, verification, code-quality, installation, architecture,
agent-workflow, and release documentation only where the public contract
changes. Add concise migration guidance for repositories whose merge base is
unmanaged.

Before tagging:

1. run the focused repository, quality, engine, release, and installed-release
   suites affected by the changes;
2. run one full merge gate for the stable candidate;
3. run the stable candidate's supplemental suites once, composing still-valid
   receipts after bounded fixes;
4. install the exact candidate tag into a fresh prefix;
5. run the complete installed-release acceptance sequence; and
6. verify the release manifest once more after the final command.

### v0.21.6 completion criteria

- Repeated Python analysis leaves the installed release byte-for-byte and
  entry-for-entry unchanged.
- Supported Pydantic declarations are not reported as dead while unrelated dead
  definitions still are.
- A repository can add Code Polishy and pass `merge-gate` against an unmanaged
  base.
- Removing or corrupting existing policy still fails closed.
- Permanent documentation and findings describe these behaviors directly.
- No new runtime dependency is added.

## v0.22: portable execution and ownership

### 1. Publish one canonical portable release

Make the verified standalone release bundle the canonical published artifact
for each supported host. It contains the same manifest and tree the existing
bundle installer already validates.

Publish, for every supported operating-system and architecture pair:

- the release archive;
- its SHA-256 digest;
- the internal release manifest;
- an SBOM and release provenance bound to the source commit; and
- a concise machine-readable index containing version, host, archive digest,
  and release digest.

The existing `install-bundle --source PATH --sha256 DIGEST --prefix PATH`
boundary remains the installer. Downloading is a CI or caller responsibility;
installation never trusts a filename, tag, redirect, or mutable channel.

### 2. Provide a digest-pinned OCI transport

Build each Linux image from the already verified Linux release bundle. Do not
build a second independent release tree inside the container.

The image must:

- support the published Linux architectures;
- run as a non-root user with `code-polishy` on `PATH`;
- keep the target checkout as its working-directory boundary;
- carry OCI labels for source commit, Code Polishy version, release digest, and
  bundle digest;
- preserve the internal launcher and manifest verification on every command;
- require users and examples to pin the image by OCI digest; and
- publish provenance for the exact image digest.

Tags may aid discovery, but no policy or CI example treats a tag as identity.
A private or self-managed GitLab instance needs only a runner that can pull the
chosen registry or a locally mirrored digest. It needs no Code Polishy GitLab
account, API token, monitoring provider, or specially preinstalled release.

Provide GitLab and GitHub examples that run the same repository command and
lock. Keep registry credentials, mirroring, and network availability outside
the Code Polishy policy contract.

### 3. Own generated test artifacts per execution

Create one directory for each execution beneath:

```text
.code-polishy-artifacts/<execution-id>/
```

Expose at least `CODE_POLISHY_EXECUTION_ID` and
`CODE_POLISHY_ARTIFACT_DIR` to the declared command. Support deterministic
argument substitution for the artifact directory without invoking a shell.

Extend test-suite declarations with exact artifact entries. The first supported
types are JUnit and Cobertura XML. Each declaration names a contained relative
path below the execution directory and whether the output is required.

After a command finishes:

1. reject an escaping, linked, special, oversized, or missing required output;
2. parse XML with external entities and document-type processing disabled;
3. verify the expected JUnit or Cobertura root shape;
4. record path, type, size, and digest in the gate report; and
5. preserve the command's own exit status as the suite result.

The artifact root is excluded from governed source and has a synchronized
ignore rule. Code Polishy may delete only completed directories carrying its
valid ownership manifest. It never follows links, touches an active execution,
or deletes an unknown entry. Parallel processes use distinct execution IDs and
leases. The current completed run remains available for CI upload; a later run
may prune older owned runs according to one documented policy.

Cross-job receipt aggregation and interpreting framework-specific test counts
remain separate features.

### 4. Separate test ownership from production direction

Retain the existing guarantees:

- every governed production executable belongs to exactly one module;
- every module has at least one quick module-scoped focused suite; and
- repository-wide behavior has at least one full suite.

Make test ownership explicit without adding test imports to the production DAG:

1. classify default and configured test paths at the repository boundary;
2. require every governed test source to belong to exactly one production
   module that it verifies;
3. require module-scoped suite paths to cover that module's owned tests;
4. keep suite-to-module ownership in `tests.suites[].modules`;
5. omit edges originating in test source from production `dependsOn`
   enforcement; and
6. continue checking production imports even when tests import the same target.

Repository-scoped integration and end-to-end suites may span modules without
creating a production dependency. Their paths remain explicit test evidence,
not architecture nodes.

Add an always-available architecture summary containing production-file count,
test-file count, incoming dependency count, outgoing dependency count, and
focused-suite count per module. These facts support review of suspiciously
large or central modules. They do not fail a build based on a module name,
percentage, line count, or degree threshold.

Do not add a heuristic “catch-all module” failure. Exact ownership, acyclic
direction, production import evidence, and focused-suite coverage remain the
blocking rules. A future blocking rule requires an objective invariant and the
normal exact, justified, owned, expiring exception contract.

### 5. Coordinate with language-pack work

The v0.22 engine boundaries should be reusable by future first-party packs:

- portable release publishing provides a model for authenticated pack
  artifacts;
- per-execution artifact directories provide bounded writable output for pack
  commands; and
- separate test ownership prevents pack-supplied import evidence from confusing
  tests with production direction.

Do not add evaluated discovery, host-toolchain approval, an official pack
catalog, or a built-in-language extraction merely to exercise these boundaries.
Those changes proceed through the dedicated language-pack plans and their own
atomic public cutovers.

### v0.22 verification

Use local archives, a local OCI registry, disposable repositories, and
temporary artifact roots for ordinary tests. Cover:

- archive, manifest, platform, and OCI digest mismatch;
- a valid locked repository running from the OCI image with no host install;
- offline bundle installation from already acquired bytes;
- non-root execution and unwritable release contents;
- concurrent artifact executions and interrupted-run retention;
- malicious links, traversal, special files, malformed XML, entities, and
  oversized artifacts;
- JUnit and Cobertura capture from passing and failing commands;
- safe pruning with unknown and active directories present;
- exact production and test ownership;
- test-only imports that do not weaken production direction; and
- deterministic architecture summaries on Linux, macOS, and Windows.

Credentialed publication and destructive registry tests remain explicit
external release gates. Supplemental hardening follows the stable-candidate
rules and does not run during ordinary implementation.

### v0.22 completion criteria

- CI can run an exact Code Polishy release from a verified archive or
  digest-pinned OCI image without a machine-global installation.
- Archive, image, lock, and internal release identities reconcile to one
  reviewed source commit.
- JUnit and Cobertura outputs stay inside one managed execution directory and
  appear with digests in the gate report.
- Cleanup cannot affect active, unknown, linked, or outside paths.
- Every production and test file has one clear module owner while only
  production imports determine `dependsOn`.
- Every module retains focused behavioral evidence.
- Architecture concentration is visible without becoming an arbitrary gate.
- The language-pack plans remain separate and internally consistent.

## Explicit non-goals

- importing or executing target Pydantic;
- target-controlled Vulture configuration or broad framework whitelists;
- treating malformed base policy as first-time adoption;
- a GitLab API integration or recurring-monitoring provider;
- mutable OCI tags as a release identity;
- parsing test output to override command success or failure;
- cross-job or sharded receipt aggregation;
- blocking modules because of generic names or fixed size thresholds; and
- moving built-in language support into packs as part of either release.
